# 사이트 클론 진행 프로세스 (표준)

> 이 문서는 새 Claude Code 세션이 "OO 사이트를 클론해줘" 요청을 받았을 때 참고하는 표준 절차입니다.
> HongHub GitHub 저장소에 있으므로, MCP의 `get_github_file`로 언제든 다시 읽을 수 있습니다.

## 핵심 원칙 — 기능은 가져오고, 브랜드는 가져오지 않는다

**클론 대상은 원본의 기능/정보구조/UX 흐름이지, 원본의 정체성이 아닙니다.**

| 가져올 것 (클론 대상) | 가져오지 않을 것 (리브랜딩 대상) |
|---|---|
| 사이트맵, 페이지 구조 | 서비스 이름 |
| 각 화면의 기능/필드/버튼 | 로고, 파비콘 |
| 데이터 모델(어떤 정보를 저장하는지) | 도메인 |
| UX 흐름(온보딩→가입→기능→결제 등) | 마케팅 카피의 브랜드 고유 표현 |
| API 연동 구조(어떤 외부 서비스와 어떻게 연동하는지) | 회사명, 저작권 표기 |
| 요금제 구조(가격은 참고, 그대로 베껴도 무방) | 원본 소유자의 상표/로고 이미지 |

**작업 중·후 반드시 확인**: 코드·DB 코멘트·README·UI 텍스트 전체에서 원본 브랜드명이 한 글자도 안 남았는지 `grep -ri "원본이름"`으로 전수 검사한다. PLAN.md류 정찰 기록에만 원본 언급이 남는 건 허용(작업 기록이라 불가피) — 단 이 파일은 git 추적 제외(`.gitignore`)해서 공개 저장소엔 안 올라가게 한다.

## 표준 진행 순서

### 0단계 — 합의
- 리브랜딩할 새 서비스명(가칭) 확인
- 원본에 로그인 계정이 있는지, 프리미엄/유료 기능이 있는지 확인(있으면 나중에 결제해서 잠금 뒤까지 봐야 함)
- **원본이 순수 웹서비스인지, 아니면 웹 밖의 컴포넌트가 필요한지 먼저 확인할 것.** 모든 클론이 "웹앱 하나"로 끝나지 않는다. 예: 유쇼츠(U-Short)는 특이 케이스로, 단순 웹 연동이 아니라 웹 밖의 컴포넌트(크롬 익스텐션 등)까지 필요한 구조다. 이런 걸 0단계에서 놓치면 나중에 범위가 커져서 재작업하게 되니, 원본 정찰(1단계) 전에 "이거 웹만으로 되는 서비스 맞아?"를 먼저 확인한다.

### 1단계 — 원본 정찰 (실제 로그인 상태로)
- 로그인 후 사이트맵 전체를 실제로 클릭하며 문서화(사이드바 최상단부터 하나도 안 빼고)
- 각 화면의 필드/버튼/모달/빈 상태 문구까지 기록
- 네트워크 탭에서 실제 API 엔드포인트/응답 구조 확인
- 전부 `PLAN.md`(git 비추적)에 자기완결적으로 기록 — "기억 없는 새 세션이 이 문서만 보고 이어갈 수 있게" 작성
- **주의**: 로그인 상태 정찰이어도 잠금 화면 뒤(유료 기능)는 못 봄. "안 보이니까 없다"고 단정하지 말고 잠금 카드 문구만 우선 기록, 프리미엄 결제 후 재정찰 예정임을 명시

### 2단계 — 기술 스택 스캐폴딩
- Next.js(App Router)+TypeScript+Tailwind, Supabase(Postgres+Auth+Storage), Vercel 배포가 기본 조합
- **⚠️ Supabase 무료 요금제는 계정(이메일)당 활성 프로젝트 2개까지만 가능.** 새 프로젝트마다 Supabase를 새로 만들면 금방 한도에 걸린다(실제로 겪음 — 오래 안 쓴 프로젝트가 자동 일시정지되고, 재개하려 해도 "2개 초과"로 막힘). 그래서 이 프로젝트군은 **기존 Supabase 프로젝트를 여러 서비스가 공유**하는 걸 기본 전략으로 삼는다 — 공유 시 테이블 접두사로 구분(예: `ut_`, `hub_`). 신규 프로젝트를 만들기 전에 "정말 새 Supabase가 필요한가, 기존 걸 공유하면 안 되나"부터 확인할 것.
- **GitHub·Vercel은 이런 제약이 없음** — 프로젝트(저장소)마다 새로 만들어도 무방.
- `.env.local`은 git 추적 제외, 값은 채팅에 평문으로 남기지 말고 파일로만 다룰 것

### 3단계 — 무료 기능부터 구현
- 랜딩, 인증, 무료 화면들을 실데이터로 구현
- 프리미엄 잠금 UX는 이 단계에서 화면만(잠금 카드) 재현, 실제 게이팅 로직은 나중

### 4단계 — 프리미엄/결제 체계
- 구독 상태 모델링, 프리미엄 게이팅 적용
- 실제 PG 연동 전까지는 "실제 결제 없이 구독 상태만 부여" 목업으로 명확히 라벨링(사용자를 속이지 않게)

### 5단계 — BYOK/외부 서비스 연동
- 사용자가 자기 키를 넣는 구조(AI API, 제휴 API 등)라면 AES-256 등으로 암호화 저장
- OAuth 연동(예: SNS 계정 연동)은 실제 개발자 콘솔 앱 등록이 필요 — 이 과정은 계정 신원 확인(전화인증 등)이 걸려있어 **사용자가 직접 수행**, Claude는 스크린샷 보고 단계별 안내만 함(대행 불가)

### 6단계 — 프리미엄 결제 후 전면 재정찰
- 실제로 유료 결제해서 1단계에서 못 봤던 화면을 마저 정찰
- 여기서 발견되는 격차가 보통 제일 큼(이 프로젝트들에서 매번 실제로 있었음) — 놀라지 말고 그대로 PLAN.md에 갱신

### 7단계 — 실사용 검증 (절대 생략 금지)
- **"빌드 통과"는 "동작 확인"이 아니다.** TypeScript 컴파일이 되는 것과 실제로 클릭했을 때 되는 것은 다른 문제.
- 배포 후 실제 브라우저로 클릭해서 확인. 안 되면 "빌드만 확인했고 실제 동작은 아직 안 봤다"고 정직하게 말할 것.
- 외부 API를 붙였다면 실제 curl/호출로 200 응답과 실데이터를 확인할 것 — 스펙 문서만 보고 "될 것 같다"고 단정하지 말 것.

### 8단계 — MCP 서버 추가 (기능 클론이 다 끝난 다음 마지막 단계)
- 모든 기능이 실사용 검증까지 끝난 뒤에 MCP를 붙인다 — 순서를 바꾸지 말 것(자동화할 대상이 완성돼 있어야 자동화가 의미 있음)
- 방법은 `MCP_GUIDE.md` 참고. 이 프로젝트(`f4fdf260-...` 등 이미 만든 MCP들)와 동일하게 Supabase 범용 CRUD + 도메인 특화 툴 + GitHub 읽기 툴 조합이 표준 패턴
- MCP까지 붙으면 Claude가 코드/DB/기능을 전부 직접 조작할 수 있는 상태 = "자동화 완료"로 간주

### 9단계 — 주기적 재대조
- 시간이 지나 원본이 업데이트됐을 수 있으니, 가끔 원본을 처음부터 다시 하나씩 눌러보며 클론과 실시간 비교
- 발견된 격차는 스코프를 임의로 줄이지 말고 전부 구현(사용자가 "클론이면 다 해야지"라고 명시적으로 요구한 원칙)
- 외부 API가 원본과 개수/스펙이 다르면(예: OAuth 권한 스코프 10개 vs 우리 6개) 정확히 세어서 맞출 것 — 대충 세지 말 것

## 자주 걸리는 함정 (실제로 겪은 것들)

- **"안 보이니까 없다"고 단정** — 로그인 세션이 실제로 있는지, 기존에 열린 탭이 있는지 먼저 확인할 것
- **API 스펙을 추측으로 구현** — 반드시 공식 문서를 찾아서 정확한 엔드포인트/파라미터/헤더로 구현. 문서가 막혀있으면(Cloudflare 등) 여러 우회 경로(캐시, 미러, 관련 블로그 이관 가이드)로 실제 스펙을 확보한 뒤 curl로 실증하고 나서 코드에 반영
- **에러 원인을 성급하게 "설정 문제"로 단정** — 외부 서비스가 API 자체를 폐지/이관 중일 수 있음(공지사항을 직접 찾아 확인한 사례 있음)
- **원본 브랜드 잔재** — grep 전수검사 없이 "다 지웠다"고 말하지 말 것
